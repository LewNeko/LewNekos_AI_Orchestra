Claude:
your own Auditor/Verifier design, OpenViking's L0/L1/L2, and 
Aider's repo-map all reduce to the same move — build a cheap structural 
index over the large space first, rank by relevance to the current task, 
and only load the small slice that matters into the model. Different 
implementations (hierarchical summaries vs. a symbol/reference graph + 
PageRank), same underlying principle: narrow before you spend tokens, and 
don't let the narrowing layer be the thing you trust — it just decides 
where to look.

Here's the specific insight worth catching before you reach for either 
tool, though: Aider's repo-map needs a structural representation to rank 
over — for code, that's the symbol/call graph (which function references 
which). You don't have that for documents... except you might already, 
for free. The_Reader's output already is that structure. Every chunk that 
goes through Reader produces {fact, claim, evidence, status} — that's 
already an index of "which chunk asserts something about which fact." 
If you aggregate Reader's outputs across all chunks into one table 
(fact → list of chunks that mention it, with what they claimed), you've 
built the exact kind of structural map Aider builds via tree-sitter 
parsing — except yours comes as a byproduct of work you're already doing, 
not a separate indexing pass over the raw document.

Concretely, that means: when Auditor needs to resolve "does chunk 42 supersede chunk 17 on Fact A," it doesn't need OpenViking or an Aider-style graph to find the relevant chunks — it can just query the aggregated Reader-output table for "every chunk that produced a claim about Fact A," which is a plain lookup, not a search. Where OpenViking/Aider-style ranking earns its keep is a layer up from that: if you're running this over hundreds of documents rather than one, and Reader hasn't touched most of them yet, then you need something to answer "which of these 500 unprocessed chunks is even worth running Reader on for Fact A" — that's a pre-filter before Reader runs, not a replacement for what Reader+Auditor already give you for its own output.

So the real design question becomes: is your bottleneck "too many chunks to run Reader on everything" (→ needs a pre-filter, OpenViking/Aider-style), or "Reader's already run on everything, now Auditor needs to find the right subset of results" (→ you already have what you need, it's just a lookup table)? Is there more context coming, or is that the question worth settling next?

Claude:
That reframing is useful, and it points at something worth naming 
directly: you've been evaluating Aider and OpenViking as chunker 
candidates, but neither of them actually does chunking — they both 
do relevance-ranking over an already-structured space. Aider's repo-map 
ranks symbols that tree-sitter already extracted as discrete units 
(functions, classes). OpenViking's L0/L1/L2 tiers presuppose something 
already carved the corpus into documents/sections it can summarize. 
Both tools start after the step you're missing. That's why neither one 
has felt like a fit — you've been looking for a chunker in the 
retrieval-and-ranking aisle, but that's genuinely a different problem 
than "take one raw document and produce bounded, addressable pieces of 
it."

Here's the part that should lower the bar on what Chunker actually 
needs to be: you already built Auditor specifically to catch what 
naive chunk boundaries miss (a claim in chunk 17, its correction in 
chunk 42). That means Chunker doesn't need to be smart about keeping 
related facts together — that's explicitly Auditor's job, not Chunker's. 
Chunker's actual bar is much lower than "intelligent segmentation": it 
just needs to produce chunks that are (a) bounded to a reasonable size 
for Reader's context, (b) aligned to structural boundaries humans would 
recognize (a paragraph, a header section, an HTML article) rather than an 
arbitrary token cutoff mid-sentence, and (c) individually addressable 
with stable IDs + positional metadata, since your whole system's 
credibility rests on being able to say "Chunk 12, Section 3.2" and have 
that mean something. That's a parsing problem, not an agentic or ranking 
problem — think python-docx walking headers, BeautifulSoup walking 
<section>/<article> tags, or splitting markdown on #/## boundaries. 
Boring, deterministic, no model call needed at all for the split itself.

The reason this connects back to what we said about Auditor last time: 
because Chunker is allowed to be "dumb" about boundaries, you don't need 
to solve document-type-agnostic intelligent chunking in one shot — you 
can build the boring structural splitter for one format first and let 
Auditor absorb the seams.

Mostly—your capability check is correct. It calls the right endpoint (/api/show) and 
correctly detects that gemma3:4b has only completion, vision.
It now produces this clear core error:
RuntimeError: Model 'gemma3:4b' does not support tools.

But it is not fully “graceful” yet, because Python still prints 
a traceback. That’s because no code in orchestrator.py catches 
the RuntimeError at the command-line entry point.
Two changes to consider:
Your if resp.status_code != 200: block will never run.
resp.raise_for_status() immediately before it already raises 
on every 4xx/5xx response. Put custom handling before that call, 
or catch the exception around it.

The check currently runs in OllamaBackend.__init__, even if a 
future caller wants ordinary chat without tools. That’s fine if this 
project is always an agent, but otherwise check only when 
chat(..., tools=...) receives tools.

Also, avoid saying every HTTP 400 means “the model may not be capable 
of tool calls.” A 400 can also mean malformed JSON, an invalid tool 
schema, or an invalid conversation history. Your metadata check is
 the reliable way to identify the unsupported-model case.
So: correct detection, but the custom HTTP message is unreachable,
 and graceful terminal output needs one final try/except
  in the CLI section.
